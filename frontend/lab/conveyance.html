Conveyance

Research into phone-held credentials and per-request human approval for authenticated MCP calls.

Status: R&D / in development

Last reviewed: 2026-09-18

View source on GitHub →Browse projects →

Move the credential away from the agent

An agent may need to make an authenticated HTTP request, but putting the credential on the same PC as the agent means a compromise of that machine can potentially reach it. Environment variables, a local config file, and a keychain that the agent process can query all share that basic problem: the computer that needs the secret is also the computer an attacker may control.

Conveyance explores a different boundary. The PC asks for a request, but a separate phone holds the credential, shows the request to a person, and executes it only after an explicit approval. It is the hardware-wallet idea applied to agent capabilities: the agent never receives the secret, and a PC-side process cannot silently turn an approval for one request into a different request.

The intended path

MCP client → shim → daemon → encrypted BLE → phone → result

The MCP shim speaks JSON-RPC over stdio and hands a narrow request to a long-lived local daemon. The daemon owns pairing, session state, local logs, and the Bluetooth connection. Over BLE, Conveyance uses an application-layer encrypted session; the security model does not depend on BLE pairing alone. The phone is meant to display the exact request, require a physical tap, use the credential it holds, and return only the result.

The approval is bound to the request payload. In other words, the request that reaches execution must match the request the person approved after canonicalization. That binding matters if the PC-side daemon is under pressure from a compromised agent: showing a harmless request and substituting an authenticated one later is precisely the kind of gap the protocol is designed to close.

What exists and what does not

The PC-side substrate is implemented: cryptographic and storage components, session and wire handling, pairing state, daemon, MCP shim, CLI, mock-phone flows, and a BLE transport. The BLE central path has been exercised over real radio against a test peripheral; the broader request path above it has been validated with the mock transport and mock phone.

That is not the same as shipping phone-approved requests. The Android work is still in progress, and a real phone performing pairing, displaying approvals, holding credentials, and executing authenticated requests is not an end-to-end workflow to rely on today. Conveyance is therefore useful as a security architecture and PC-side substrate, with mock-phone validation, rather than as a finished everyday credential broker.

Exploring the substrate

Developers can build the Rust workspace, run the daemon and MCP shim, inspect logs, and exercise the supported mock-phone path. The repository's setup instructions cover the OS-keychain requirement, configuration, command surface, and feature flags. A missing keychain is treated as a startup error rather than quietly falling back to weaker storage.

The important expectation is modest: this is a way to study and test the boundary, not a promise that a real phone can approve production requests today. The architecture and phase documents are the right place for protocol choices, state machines, and implementation status.

What the model does not solve

Conveyance makes a deliberately strong claim only about the separation it is trying to create. A compromised PC should not be able to extract a credential it never holds, forge a phone approval, or execute an approved request with a substituted payload. A compromised phone is a different outcome: it holds both the credentials and the approval authority, so it is the high-value endpoint.

The design also does not make radio jamming, traffic analysis, physical coercion, or every kind of endpoint compromise disappear. It uses established primitives and keeps the application session above BLE as a separate security layer, but it is not a substitute for understanding the phone, service, and human trust boundaries around a request.
