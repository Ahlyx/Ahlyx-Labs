AuditMCP

A local-first MCP proxy that keeps a reviewable record of tool calls without turning itself into a policy gateway.

Status: Local tool

Last reviewed: 2026-09-18

View source on GitHub →Browse projects →

Why keep an MCP audit trail?

MCP makes it easy to connect an agent to useful tools, but that convenience can leave an awkward question after a session: what did the agent actually ask those tools to do? AuditMCP sits between a compatible client and server so a local user can answer that question from a durable record instead of a terminal scrollback buffer.

It is deliberately a recorder, not a decision-maker. AuditMCP forwards MCP traffic and records matching tools/call activity; it does not decide whether a request is authorized, scan a server for vulnerabilities, or try to become an enterprise gateway. That narrow scope is useful when the goal is accountability without inserting another policy engine into an agent's critical path.

What it does today

The proxy supports stdio servers and loopback HTTP listeners. Tool-call records go to a local SQLite database, where they can be queried, verified, or exported as JSONL. The default design keeps the data on the same machine: no account, telemetry service, or cloud log store is required.

Proxy first, log second

MCP client → AuditMCP proxy → MCP server
                 │
                 └→ local SQLite audit log → query / verify / export

AuditMCP forwards the request and response while a dedicated local write path records the tool call. Likely secrets are redacted before anything is persisted, so a saved record can still be useful without casually copying credentials into the database. The log chain is designed to make later changes evident: each entry links to the previous one, and the current implementation adds keyed integrity, heartbeat, and anchor mechanisms around that history.

That is evidence, not magic. The log is tamper-evident rather than tamper-proof, and an attacker with control of every relevant local secret and file can defeat its protections. AuditMCP also intentionally fails open after startup: if logging fails during a session, the tool call continues. Losing an audit entry is visible and undesirable, but blocking an agent because a local log writer hiccupped would turn the observer into an availability dependency.

Where it fits

The usual setup is to wrap an MCP server command in a client configuration, then inspect the local history after a session. For a stdio server, the shape is small enough to try without a config file:

auditmcp run -- npx -y @some/mcp-server
auditmcp query
auditmcp verify

Release archives are available for supported desktop platforms, or the Rust source can be built locally. HTTP proxying is loopback-only and maps each local listener to one upstream, which is appropriate for a local audit tool rather than a remotely exposed service.

Trust boundaries and limits

Redaction is pattern- and heuristic-based. It is intentionally conservative, but no pattern set can promise to recognize every secret format. A hash chain can reveal many kinds of alteration, reordering, or interior deletion; it is not a universal append-only ledger. Treat the database as sensitive audit material even when redaction is working.

Interactive OAuth is also a real boundary. A transparent local proxy changes the identity and URL that an MCP client sees, while OAuth discovery depends on those identities agreeing. AuditMCP does not rewrite that security check to make transparent proxying appear to work. Static authorization headers can pass through without being stored; interactive OAuth flows do not fit this proxy model.

The project does not defend against a malicious MCP client that bypasses it, and it does not enforce a permission policy. Its value is a local, inspectable account of the tool calls that actually pass through it.
