Conveyance

Research and development toward authenticated MCP requests that are approved and executed by a separate phone holding the credentials.

Status: R&D / in development

Last reviewed: 2026-09-17

View source on GitHub →Browse projects →

Overview

Conveyance explores a capability broker for agents that need authenticated HTTP requests without placing credentials on the PC where the agent runs. It is intended for security-focused MCP experimentation. A concrete use case is an agent requesting a protected action that a human reviews on a second device before the request is executed.

What currently works

The maintained README reports PC-side phases 0–9 as implemented: a Rust crypto/storage/session substrate, daemon, MCP shim, CLI, mock-phone verification, and BLE transport work. The phone side is not a shipping workflow.

Roadmap

Android phase 10 is scaffolding only. It has no implemented credential store, pairing, approval UI, BLE protocol, or auth flows; real-phone approval and real-hardware end-to-end use remain later work.

How it works

MCP client → shim → local daemon → encrypted BLE → phone approval/execution → result

The target architecture assigns pairing, sessions, and an execution log to the PC side while the phone would hold credentials and approval authority. The maintained source distinguishes that target architecture from the current mock-phone demonstration.

Getting started

The PC substrate builds with stable Rust (the reviewed README lists MSRV 1.90) and an available OS keychain. The documented build is cargo build --release -p conveyance --features ble. The CLI exposes setup, pairing, daemon, session, and log commands, but current real-device pairing is blocked by the unfinished phone application.

Security, privacy, and limitations

The project's intended credential isolation must not be read as a completed day-to-day phone approval product. The source documents mock-phone end-to-end testing, a BLE transport radio check, and limits around physical phones, real keychains, and manual platform validation. A compromised phone is outside the intended protection boundary.
